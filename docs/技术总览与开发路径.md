## 1. 一句话

**游伴是一个「游戏进度陪伴器」**：玩家告诉它自己玩到哪了（拖进度条 / 选章节），它给出不剧透的章节地图、Boss 与存档点、成长历程、玩家舆情，并提供一本**随进度走的 AI 攻略簿**。游戏库是买手店式的多平台精选（当前 17 款），不依赖任何单一平台账号。

## 3. 关键设计决定（以及为什么）

| 决定 | 理由 | 代价 / 何时重新评估 |
|---|---|---|
| **客户端只认一个 BFF，不直连 Supabase** | 密钥只在服务端；公网暴露面只有一个进程；日后换库 / 换模型客户端无感 | BFF 要代理所有读写。用户量上来后可让只读内容走 CDN |
| **BFF 零依赖 Node** | 供应链面最小、部署就是拷文件、冷启动快 | 路由与校验手写。端点超过约 30 个或多人协作时，建议换 Fastify + 类型校验 |
| **前端无打包器** | 离线可跑、启动快、Electron / Tauri / 网页同一套产物 | 全局命名空间、无 tree-shaking、无类型。见讨论点 D1 |
| **账号底座用 Supabase Auth** | 已部署、RLS 现成、后续手机号 / 微信是给同一 `user_id` 挂新登录方式 | 内测期账号名映射为内部邮箱，见账号设计文档 |
| **进度「拖到哪存到哪」，后写为准** | 进度是玩家主观声明，没有合并语义 | 多端同时拖动时后者覆盖前者，可接受 |
| **AI 不做全量历史入 prompt** | 长程对话成本与延迟可控；防剧透边界在服务端切简报时执行 | 状态卡质量决定长程体验，见 gbot 文档 |
| **游戏内容 jsonb 整文档** | 客户端消费的就是文档形状，拆表徒增同步成本 | 需要跨游戏检索 / 运营后台时再拆 |

## 5. 安全边界（硬规矩）

- **进客户端的只有用户自己的 token。** `SERVICE_ROLE_KEY` / `JWT_SECRET` / `GLM_API_KEY` / `STEAM_API_KEY` 只存在服务器 `.env`（权限 600，属主 `youban`）。
- 公网只有 nginx 443 的一条路径；Postgres、Kong、两个 BFF 全部只绑 `127.0.0.1`。
- 滥用护栏：nginx 每 IP 每分钟 30 次；对话每身份每日 60 轮；登录同账号 10 分钟错 5 次锁 10 分钟；注册须邀请码。
- 防剧透在**服务端**执行：进度之后的内容根本不进 prompt，而不是靠模型自觉。

**已知欠账（须处理，见第 7 节）**
- GitHub 仓库是 **Public**，其中含服务器主机名、目录结构、部署脚本（不含任何密钥）。
- GLM key 曾在聊天中明文出现，**尚未轮换**。
- 主站 `offcircle-studios.com` 的 TLS 证书 2026-09-01 已过期（与游伴无关，但同机）。
- 对外 API 目前借用 `comfyui-internal` 子域，未用独立域名。

### 已完成（截至 2026-09-30）

| 后端底座 | 自托管 Supabase、业务表与 RLS、games 表 seed、Steam BFF |
| AI 攻略簿 | 流式对话、按进度切简报、状态卡长程记忆、战报导出、线上部署 |
| 公网入口 | HTTPS 反代、限流、每日配额；网页零配置直连 |
| 宽屏 | ≥1024px 三栏桌面布局 |
| **账号与同步** | 内测账号（账号名 + 密码 + 邀请码）、进度跨端同步、攻略簿按账号归属、设备簿认领 |
| 桌面客户端 | Tauri v2 Windows 安装包（NSIS + MSI） |

## 7. 需要讨论并拍板的事项

每项给出我的建议，方便直接表态同意或否决。

### 产品 / 合规

| 编号 | 问题 | 建议 |
|---|---|---|
| **P1** | 仓库是 Public。是否转 Private？ | **转 Private**。Pages 在私有仓库需付费方案，或把静态站改由自己的服务器托管（同一 nginx，多一个 location）。代码里没有密钥，但部署细节不宜公开 |
| **P2** | 内测范围与邀请码发放方式 | 当前一个通用邀请码。建议改为**一人一码**（可作废、可溯源），人数上 20 后再做 |
| **P3** | ICP 备案进度与正式域名 | 备案是手机号登录、小程序、正式对外的共同前置。先定域名 |
| **P4** | 《用户协议》《隐私政策》目前是占位文字 | 开放给团队外的人之前必须有真实文本；对话内容会发送给第三方模型服务商这一点须写明 |
| **P5** | 对话数据保留多久、用户能否导出 / 删除全部数据 | 建议提供「删除账号及全部数据」入口（数据库层已是级联删除，只差界面） |

### 架构

| 编号 | 问题 | 建议 |
|---|---|---|
| **D1** | 前端是否引入打包器与 TypeScript | **暂不**。当前规模（约 2k 行 JSX）无打包器的收益大于成本。触发条件：多人并行开发前端，或要上小程序（那时评估 Taro 重写） |
| **D2** | BFF 继续零依赖，还是换框架 | 继续零依赖到 N3 完成；合并 Steam 端点时一并评估 Fastify + schema 校验 |
| **D3** | 两个 BFF 合并还是并存 | **合并为一个对外进程**。Steam BFF 自己签发会话 JWT，与 Supabase Auth 的 token 是两套身份，长期并存会出现「登录了但 Steam 端点不认」 |
| **D4** | 客户端要不要直连 Supabase（PostgREST + RLS） | **不要**。RLS 已经配好可作纵深防御，但公网只暴露 BFF |
| **D8** | 单机部署。是否需要高可用 | 内测期不需要。先做备份（N9）与监控（N8）；用户破千或对外收费前再谈多机 |
| **D9** | 小程序走哪条路 | 维持原结论：小程序是独立运行时，Tauri 覆盖不了，须单独一条线。排在 App 之后 |

### AI（详见 gbot 文档）

| 编号 | 问题 | 建议 |
|---|---|---|
| **D5** | 模型供应商单一（智谱） | provider 接口已抽象。建议接第二家做对照与灾备，由评测集决定主力 |
| **D6** | 知识从哪来：只靠手写游戏 JSON，还是引入检索 | 先把手写 JSON 的覆盖面量化（评测集），再决定是否上检索。不要先建向量库再找问题 |
| **D7** | 「提到下一个 Boss 的名字」算不算剧透 | 这是产品定义，不是技术问题。当前简报**有意**包含下一个 Boss 名。需要王彪定标准，然后写进评测 |
