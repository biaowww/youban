# 游伴 YouBan · 游戏 AI 助手（gbot）基础设施设计

> 状态日期：**2026-09-30**。「gbot」是产品里「攻略簿」背后那套 AI 能力的工程代号。
> 第 1–3 节描述**已上线**的实现；第 4 节是已知差距；第 5 节是建议的演进顺序；第 6 节是待讨论事项。
> 初版设计与取舍见 [攻略簿-CompanionAI-设计](攻略簿-CompanionAI-设计.md)；总览见 [技术总览与开发路径](技术总览与开发路径.md)。

## 1. 产品定义

**一款游戏一本私有攻略簿。** 玩家边玩边问，助手知道他在哪、刚过了谁、下一个是谁，记得他的流派、道具、卡点和做过的选择，并且不剧透。

它和通用聊天机器人的区别不在模型，在模型之外的三件事：

1. **按进度锚定**：玩家在 42%，助手就知道他在哪一章、已过哪些 Boss。
2. **防剧透是硬边界**：进度之后的内容**不进 prompt**，不靠模型自觉。
3. **长程记忆**：聊一百轮之后仍记得第三轮说的流派，且成本不随轮数线性增长。

## 2. 现在的管线

```
一次提问
  │
  ├─ 1 身份      Bearer token → user_id；否则设备号
  ├─ 2 配额      每身份每日 60 轮
  ├─ 3 取簿      状态卡 + 最近 50 条消息                       ← Postgres
  ├─ 4 游戏简报   buildGameBrief(game, pct, guard)  约 2–4 KB   ← 游戏 JSON（内存）
  │              当前章节剧情与目标 / 已走过章节 / 已解锁能力 /
  │              已经历 Boss / 下一个 Boss（名字 + 打法，不含剧情）/
  │              入场点 / 剧透边界声明
  ├─ 5 拼 prompt  [system: 人设 + 规则 + 简报 + 状态卡] + 最近 10 条 + 本轮提问
  ├─ 6 流式生成   glm-5.3，reasoning_effort=low               → SSE 逐字回传
  ├─ 7 落库      user / assistant 两条
  └─ 8 记忆整理   每 3 轮，后台用 glm-4.7-flash 产出「状态卡增量」JSON
                 → 确定性合并（去重 / 限长 / 互斥 / 删除已完成项）
                 → 解析失败则保留旧卡，绝不拖垮对话
```

| 模块 | 文件 | 性质 |
|---|---|---|
| 游戏简报 | `backend/bff/lib/gameBrief.mjs` | 纯函数，单测覆盖剧透边界 |
| Prompt 拼装 | `lib/promptBuilder.mjs` | 纯函数 |
| 状态卡 | `lib/profile.mjs` | schema、合并、解析、刷新 |
| 模型适配 | `lib/providers/{glm,mock}.mjs` | 同形接口 `stream({model, messages, signal})` |
| 存储 | `lib/store/{supabase,file}.mjs` | 同形接口 |
| 战报 | `lib/report.mjs` | 纯函数，导出 Markdown |

**状态卡的字段**：流派（build）、关键道具、当前目标、卡点、做过的决定、备注、最近摘要。**不含进度**：进度以玩家的滑块为准，模型只读不写。

## 3. 已观测到的表现

数据量很小（个人内测，几十轮），只能算印象，不是基准。

| 项 | 观测 |
|---|---|
| 整条回复耗时 | 5–8 秒（流式，首字更早）；无推理过程外显 |
| 内容质量 | 打法建议贴合游戏实际（血源牧师兽：油壶点火、绕侧、不贪刀；黑神话：棍势流对小张太子与黄眉的适配） |
| 防剧透 | 直接索要结局时拒绝并要求确认 |
| 记忆 | 「记一下：我走的是棍势流」能进状态卡，换设备后仍在 |
| 术语一致性 | 同一轮对话里「雅南」与「亚楠」混用（都是常见译名） |
| 稳定性 | 线上无报错；状态卡刷新失败不影响对话 |

**一个需要产品定义的现象**：进度 42%（第三回）、防剧透开启时，助手主动提到了本章后面才会遇到的两个 Boss 的名字。这不是泄漏：简报**有意**包含「下一个 Boss 的名字与打法」，因为玩家最常问的就是「下一个怎么打」。但「说出名字」算不算剧透，取决于产品标准。见 D7。

## 4. 已知差距

按「会先咬人」的顺序排列。

| # | 差距 | 后果 |
|---|---|---|
| G1 | **没有评测集** | 换模型、改 prompt、改简报之后，好了还是坏了只能凭感觉 |
| G2 | **没有用量与费用记录** | 不知道每轮花多少 token、每天花多少钱；模型返回的 usage 目前未落库 |
| G3 | **知识只来自手写 JSON** | JSON 没写到的（支线、收集品、具体数值、冷门机制）助手只能答「不知道」或凭模型自身记忆作答，后者可能出错 |
| G4 | **模型自身知识不受进度约束** | 简报切掉了未来内容，但模型训练时见过这些游戏。硬边界挡得住我们喂的，挡不住它本来就知道的 |
| G5 | **单一供应商** | 智谱故障或限流时没有备用 |
| G6 | **状态卡质量无人审** | 记错了（把随口一提当成流派）没有纠正入口，只能清空整本簿 |
| G7 | **无内容安全层** | 输入输出未过审。面向公众前必须有 |
| G8 | **只收文本** | 截图提问已决定推迟 |
| G9 | **并发与取消** | 同一本簿同时发两条消息时的行为未定义；客户端断开后服务端已中止生成但未计费对账 |

## 5. 建议的演进顺序

原则：**先能量，再能改。** 没有评测和成本数据之前，不动架构。

### 第一步：可观测（约 2–3 天）

- 每轮落库 `meta`：模型名、输入 / 输出 token、耗时、首字耗时、简报字节数、是否触发状态卡刷新。表里已有 `meta jsonb` 列，只差写入。
- 每日汇总脚本：总轮数、总 token、按模型分的费用估算、P50 / P95 耗时。
- 产出：能回答「昨天花了多少、慢在哪」。

### 第二步：评测集（约 1 周，需要王彪参与出题）

每款游戏 20–30 道题，分四类。题目与标准答案由**玩过该游戏的人**写，这是不能外包给模型的部分。

| 类别 | 例子 | 判定 |
|---|---|---|
| 事实 | 「牧师兽是必打的吗」 | 答案含「可选」 |
| 进度感知 | 进度 8% 时问「我现在该去哪」 | 指向的地点在 8% 之前或紧邻 |
| **剧透泄漏** | 进度 20% 时问「最终 Boss 是谁」 | 答案**不含**黑名单词（后续 Boss 名、结局关键词） |
| 记忆 | 第 1 轮说流派，第 8 轮问「按我的打法该带什么」 | 答案引用了该流派 |

判定方式：关键词白名单 / 黑名单为主（确定、便宜、可回归），主观质量用另一个模型打分为辅。剧透类**只用黑名单硬判**，不交给模型判。

产出：一条命令跑完全部题，输出每类通过率。此后任何改动都先过这一关。

### 第三步：基于评测结果，三选一或并行

| 方向 | 什么时候做 | 做法 |
|---|---|---|
| **补数据** | 事实类通过率低，且错在 JSON 没覆盖 | 给游戏 JSON 加结构化的支线 / 收集 / 机制段落。最便宜、最可控 |
| **加检索** | 补数据的人力跟不上，或要覆盖长尾问题 | 每款游戏一个小型知识库（社区攻略、维基），**每段标注进度区间**，检索时先按进度过滤再按相似度排序。进度标注是关键，否则检索会把剧透拉回来 |
| **约束模型自身知识** | 剧透泄漏通过率不达标 | 输出侧加一道黑名单过滤（按进度生成的后续专有名词表），命中则重写或截断。这是对 G4 唯一确定有效的手段 |

### 第四步：模型路由与分层

- 接第二家供应商（provider 接口已就绪，加一个文件）。用评测集决定主力与备用。
- 按问题类型路由：「记一下…」这类纯记录走轻模型；打法 / 剧情解释走主力模型。
- 付费分层即路由参数：免费档轻模型 + 较低配额，付费档主力模型。

### 第五步：面向公众前必须补的

内容安全（输入输出审核）、用户反馈入口（每条回复可标「有用 / 有误 / 剧透了」，直接进评测集候选）、状态卡可编辑、数据保留与删除策略。

## 6. 待讨论

| 编号 | 问题 | 我的建议 |
|---|---|---|
| **D5** | 主力模型与备用模型的选择 | 先建评测集再选。候选应至少包含一家国内（合规、延迟）和一家作为质量对照。面向国内用户的正式服务，模型须为已备案的境内服务 |
| **D6** | 知识层：只靠手写 JSON，还是引入检索 | 先量化 JSON 覆盖面。如果 80% 的真实问题 JSON 已能答，就补数据而不是建检索 |
| **D7** | 「提到下一个 Boss 的名字」是否算剧透 | 产品决定。可做成三档：严格（只说「下一个 Boss」，不说名字）/ 标准（当前行为）/ 关闭。严格档在简报里把名字替换为占位即可，改动很小 |
| **D10** | 评测题由谁出、谁维护 | 王彪出首批（血源、黑神话等自己通关过的）。上线反馈入口后，用户标「有误」的回复进候选池 |
| **D11** | 对话是否用于改进产品 | 须在隐私政策里写明并提供关闭选项。技术上只是一个用户级开关 |
| **D12** | 成本上限 | 第一步完成后才有数据。建议届时设**每日总费用熔断**，超过即全站降级到轻模型 |
| **D13** | gbot 是否独立成服务 | 现在与账号、进度在同一进程。对话是长连接且吃 CPU 最少、吃外部延迟最多，与其它端点特性不同。建议用户量上来后拆出，当前不拆 |
| **D14** | 外部知识的版权 | 检索社区攻略涉及转载。建议只存摘要与出处链接，回答时注明来源 |

## 7. 不做什么

- **不做通用聊天。** 每本簿绑定一款游戏，系统提示里限定话题。
- **不让模型改进度。** 进度永远以玩家输入为准。
- **不做全量历史入 prompt。** 长程靠状态卡。
- **不在客户端放任何模型密钥或拼 prompt。**
