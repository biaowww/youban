# 游伴 YouBan · 跨端架构与登录授权方案

> v0.1 草案 · 2026-06-13 · 状态：**待评审，未动代码**

这份文档只做方案与决策，不含实现。回答三个问题：

1. 怎样从 Electron 迁到 Tauri，分支怎么管理；
2. 微信小程序 / iPhone / PC 三端，前端代码用哪种共享策略（**核心待决策项**）；
3. 接入 Steam / WeGame / TapTap 登录授权，架构上要补什么。

---

## 1. 决定结论的几个技术前提

在选方案之前，有几条已核实的事实直接框定了可行边界：

- **Tauri v2 自 2024 年 10 月起为稳定版**，原生支持 iOS / Android / PC（Win/Mac/Linux），前端复用同一套 web 代码（运行在系统 WebView 中）。但并非所有桌面插件都已移植到移动端。
- **Tauri 覆盖不了微信小程序。** 小程序运行在微信自有的运行时（WXML/WXSS/JS 沙箱），既不是浏览器也不是 WebView 应用，Tauri 无法打包小程序。
- **Steam 登录用 OpenID 2.0 拿到 SteamID**（身份），**读游戏库 / 时长 / 成就要用服务端 Web API Key**（`GetOwnedGames`、`GetPlayerAchievements` 等）。两条硬约束：用户 Steam 资料需设为公开；**API Key 绝不能放进前端 / 小程序**，必须在服务端调用。

**由此得到的第一条结论——三端不是"一套代码全平台"，而是天然分成三块：**

| 模块 | 覆盖范围 | 技术载体 |
|---|---|---|
| **A 块** | PC + iPhone（+ Android） | **Tauri**，复用一套 web 前端 |
| **B 块** | 微信小程序 | 独立运行时，**必须单开一条线** |
| **C 块（公共后端 BFF）** | 三端共用 | 托管密钥、跑登录授权、聚合平台数据 |

无论前端怎么选，**C 块（BFF 后端）都是必需的**——这是后面登录授权一节的核心。

## 2. Tauri 迁移

### 2.1 分支策略

| 分支 | 角色 | 说明 |
|---|---|---|
| `electron` | **测试 / 回归基线** | 保留现状，npm start 随时验证功能逻辑 |
| `tauri` | **主 release 分支** | 新建，跨端发布从这里出 |
| `master` | 稳定汇总 | 阶段成熟后合入 |

建议从当前 `electron` 切出 `tauri`，**前提是先清掉工作区里那个损坏的 `renderer.js`**（见第 5 节 Phase 0），否则会把坏文件带进新分支。

### 2.2 现有代码能平移多少

游伴前端是**纯 HTML / CSS / 原生 JS**（`renderer/`），没有重框架依赖，这对迁移极其有利——前端几乎可以原样搬到 Tauri 的 WebView 里。真正要改的是与"外壳"耦合的部分：

| Electron 现状 | Tauri 对应 | 工作量 |
|---|---|---|
| `main.js` 主进程 + `ipcMain` 加载本地 JSON | Tauri command（Rust）读文件，或前端直接 `fetch` 本地/远端数据 | 中 |
| `preload.js` contextBridge | Tauri `invoke` API | 小 |
| `electron-builder` 打包 | Tauri bundler（`tauri build`） | 中（含签名/移动端配置） |
| 窗口 420×780 配置 | `tauri.conf.json` | 小 |

风险点：移动端 WebView 与桌面 Chromium 的 CSS/字体渲染差异（本地 Noto Sans SC 字体需在移动端重新验证）、iOS 打包需 Mac + 开发者账号、部分桌面能力在移动端缺失。

## 3. 三端前端共享策略对比 ⭐ 核心待决策项

你要的就是这一节——三种走法摆在一起看清利弊，**先不拍板**。

### 方案 A：纯 web 复用 + 小程序独立降级版

PC / iOS 用 Tauri 直接包现有 `renderer` 前端；小程序作为单独的简化版本另写。

### 方案 B：上跨端框架统一重写（Taro / uni-app）

用 Taro（React 系）或 uni-app（Vue 系）把前端重写一遍，一套代码编译到**小程序 + H5 + App**；Tauri 加载其 H5 产物作为 PC/iOS 外壳。

### 方案 C：各端独立

PC/iOS（Tauri）、小程序、未来 App 各自独立代码库。

### 对比

| 维度 | A 纯 web 复用 | B 跨端框架重写 | C 各端独立 |
|---|---|---|---|
| **对现有代码** | 几乎原样复用 ✅ | **整体重写** ❌ | 部分复用 |
| **首版到 PC/iOS 速度** | **最快** ✅ | 慢（先搭框架） | 中 |
| **小程序质量** | 降级版，需单独维护 | **原生级，一并产出** ✅ | 最好但成本最高 |
| **长期一致性 / 维护** | 两套前端易分叉 ⚠️ | **一套代码最统一** ✅ | 最差，三套各自漂移 ❌ |
| **登录授权复用** | 走公共 BFF，问题不大 | 走公共 BFF | 走公共 BFF |
| **学习 / 改造成本** | 低 | 高（Taro+Tauri 组合较少见） | 高 |
| **风险** | 低 | 中（框架适配坑、Tauri 整合非主流） | 高 |

### 倾向性建议（供参考，最终由你定）

**分阶段、先 A 后按需引 B**：第一阶段用方案 A 把 PC/iOS 用现有代码快速跑通拿到可用产物；微信小程序作为独立一条线，用 Taro 单独做（小程序本来就绕不开专门适配）。**不建议一上来就全 Taro 重写**——会拖慢最有把握的 PC/iOS，且把现有能跑的代码推倒。若后期发现两套前端维护成本过高，再评估把 web 前端整体迁到 Taro 统一。

## 4. 登录与游戏平台授权设计

### 4.1 为什么必须有 BFF（Backend-for-Frontend）后端

- **密钥安全**：Steam Web API Key、各平台 OAuth client secret 不能放进前端或小程序（会被反编译/抓包窃取），必须由服务端持有。
- **OAuth / token 交换**：授权码换 token、刷新 token 都应在服务端完成。
- **跨端统一**：三端登录态、游戏库数据通过同一套 BFF 接口拉取，避免每端各写一遍平台对接逻辑。
- **绕开小程序限制**：小程序网络请求域名白名单、无法直连部分平台，统一走 BFF 最省事。

### 4.2 各平台接入现状与路径

| 平台 | 登录 | 读数据 | 现实评估 |
|---|---|---|---|
| **Steam** | OpenID 2.0（跳转 steamcommunity 登录回调拿 SteamID） | 服务端 Web API Key：`GetOwnedGames`（库+时长）、`GetPlayerAchievements`（成就） | **最成熟，优先做**。约束：用户资料需公开；OpenID 2.0 协议较老但仍可用 |
| **TapTap** | TapTap 开发者 OAuth / 登录 SDK | 取决于其开放接口范围 | 需注册 TapTap 开发者、申请权限 |
| **WeGame** | 无成熟的官方开放 API | — | **现实里最难**。短期建议"手动导入 / 账号绑定占位"，把官方接口列为长期观察项 |

> "二饼"类应用的做法基本是：官方 API + 用户显式授权 + 部分平台手填/导入兜底。游伴可沿同样思路，**先把 Steam 这条最完整的链路打通做标杆**。

### 4.3 鉴权回调在各端的差异

- **桌面 / 移动（Tauri）**：在系统浏览器打开平台登录页，登录后通过 **deep link（自定义 URL scheme）** 跳回应用；BFF 完成 token 交换后下发应用自己的会话 token。
- **小程序**：在小程序内嵌 WebView 或 H5 中转页完成第三方授权，回调到 BFF 再回小程序。

### 4.4 数据与隐私

- 数据模型大致三张表：**用户**、**平台账号绑定**（user ↔ steam/tap/wegame）、**游戏库同步缓存**。
- 合规：面向中国市场需符合《个人信息保护法》，平台 token 加密存储、最小化收集、提供解绑与数据删除。

## 6. 需要你拍板的决策项

1. **三端共享策略**：A / B / C 选哪个（建议先 A，小程序单独 Taro）。
2. **后端技术栈与托管**：自建服务 还是 云函数 / Serverless；放国内云（合规、访问速度）还是其他。
3. **小程序优先级**：是否首版就要，还是 PC/iOS 先行、小程序后置。
4. **Steam 资料公开限制**：如何向用户说明、对私密资料如何降级处理。
5. **WeGame 短期策略**：接受"手动导入占位"还是等官方接口。
